
> [!NOTE]
> 예시에서는 배열, 객체처럼 원시 값이 아닌 타입을 **참조로 비교**합니다. 즉, 왼쪽 값이 가리키는 메모리상의 대상과 오른쪽 값이 가리키는 대상이 **같은지**를 확인합니다. 그래서 내용이 같아 보여도 서로 다른 배열이나 객체를 만들었다면 비교 결과는 `false`가 됩니다.

Q. 그렇다면 원시 타입은 메모리 위치를 비교하지 않나? 또 이런 값들은 어디에 저장될까?

A.
- JavaScript의 원시 타입(`number`, `string`, `boolean`, `null`, `undefined`, `symbol`, `bigint`)은 `===` 비교 시 **값 자체**를 비교
- 객체와 배열은 `===` 비교 시 **같은 참조인지**를 비교
- 원시 값은 스택, 객체/배열은 힙에 저장

```js
// 원시 값: 값 자체를 비교
let a = 42;
let b = 42;
a === b; // true

// 객체: 참조를 비교
let x = [];
let y = [];
x === y; // false
```

Q. React.memo 설명을 보면 "단순 함수 컴포넌트"와 "비교 함수"라는 두 경우가 나오는데, 두 개가 어떻게 다르지?

A. 둘 다 결국은 "props가 바뀌었는가?" 를 판단하는 방식

기본 동작
- React.memo(MyComponent)처럼 두 번째 인자 없이 사용하면, React는 기본적으로 props를 얕게 비교(shallow compare)
- 이전 props와 새 props가 같다고 판단되면 리렌더링을 건너뜀

비교 함수를 직접 주는 경우
- React.memo(MyComponent, (prevProps, nextProps) => ...)처럼 비교 함수를 넘기면, React는 그 함수 결과를 기준으로 렌더링 여부를 결정

<br/>

> [!NOTE]
> React.memo를 사용하더라도 props 외의 다른 의존성이 바뀌면 컴포넌트는 다시 렌더링될 수 있습니다.

Q. props가 바뀌지 않았는데도 컴포넌트가 다시 렌더링되는 경우가 있다고 하는데, 어떤 상황이지?

A. React.memo는 props 기준으로 부모로부터 전달되는 재렌더링을 건너뛰게 해주는 최적화.
그래서 props 외의 다른 값이 바뀌면 리렌더링이 발생할 수 있음.

대표적인 예가 context.

const ThemeContext = React.createContext('light');

const MyComponent = React.memo(() => {
  const theme = useContext(ThemeContext);
  return <div>{theme}</div>;
});

이 경우 ThemeContext의 값이 바뀌면, props가 그대로여도 MyComponent는 다시 렌더링될 수 있음

context 값 변경
외부 스토어 구독값 변경
...

Q. import()를 클릭 이벤트 안에서 호출하면 왜 지연 로딩이라고 하는지

A. 일반 import는 보통 파일 상단에서 사용하고, 번들러가 이를 분석해 초기 번들에 포함시킴.

import { something } from './module.js';

반면 import()는 런타임에 실행되는 동적 import이며, Promise를 반환.

```js
button.addEventListener("click", () => {
  import("/non-critical.js").then((module) => {
    // ...
  });
});
```

이 문법을 사용하면 번들러는 해당 모듈을 별도 청크(chunk) 로 분리할 수 있음. 
그래서 초기 로딩 때는 포함하지 않고, 실제로 필요해지는 시점에 비동기로 불러옴.

<br/>

> [!NOTE]
> React.lazy는 동적 import와 함께 사용되며, 즉시 사용할 수 없는 컴포넌트를 나중에 불러올 수 있게 해줍니다.

Q. React.lazy(() => import('./Sidebar')) 같은 코드는 정확히 어떤 의미인지? 왜 컴포넌트가 아니라 Promise를 넘기는 거지?

A. 

```js
// 정적 import
import Sidebar from './Sidebar';

// 동적 import + React.lazy
const Sidebar = React.lazy(() => import('./Sidebar'));
```

- import('./Sidebar')는 실행 즉시 컴포넌트를 반환하는 것이 아니라, 나중에 모듈을 주겠다는 Promise를 반환.
- 파일을 읽거나 받아오는 과정이 비동기일 수 있기 때문.

- React.lazy는 이 Promise가 끝날 때까지 기다렸다가, 준비가 되면 해당 컴포넌트를 렌더링
- 그리고 기다리는 동안 보여줄 UI는 Suspense의 fallback이 담당
- 추가로, 이 패턴은 보통 기본 내보내기(default export) 를 기대

```js
const Sidebar = React.lazy(() => import('./Sidebar'));
```

즉, ./Sidebar 모듈이 default export로 컴포넌트를 내보내는 구조.

<br/>

> [!NOTE]
> Suspense는 비동기 준비 상태를 상위 경계에서 처리한다는 점에서 try/catch와 비슷하게 비유되곤 합니다.

Q. Suspense가 try/catch와 비슷하다고 하는데, 정확히 무엇이 같고 무엇이 다른 건지

A. 공통점은 둘 다 어떤 문제 상황을 상위 경계(boundary) 에서 처리함

| 구분 | `try/catch` | `Suspense` |
| --- | --- | --- |
| 처리 대상 | 에러(예외) | 아직 준비되지 않은 로딩 상태 |
| 동작 방식 | 에러를 `throw`하고 `catch`에서 잡음 | 컴포넌트가 `Promise`를 던지고 `Suspense`가 잡아서 `fallback` 표시 |
| 결과 | `catch` 블록 실행 후 끝 | `Promise`가 resolve되면 다시 렌더링 시도 |
| 적용 대상 | 동기 코드 | 비동기 렌더링 (`lazy`, data fetching 등) |

다만 둘은 완전히 같은 개념X
- try/catch는 자바스크립트 언어 차원의 예외 처리
- Suspense는 React 렌더링 과정에서 비동기 대기 상태를 UI 차원에서 처리하는 메커니즘

Q. 고차 컴포넌트가 정확히 무엇인지, 그리고 훅과 비교하면 어떤 차이가 있는지

A. HOC(Higher-Order Component)는 컴포넌트를 받아서 새 컴포넌트를 반환하는 함수

```js
function withAuth(WrappedComponent) {
  return function AuthenticatedComponent(props) {
    const isLoggedIn = useAuth();

    if (!isLoggedIn) return <Redirect to="/login" />;
    return <WrappedComponent {...props} />;
  };
}

const ProtectedPage = withAuth(MyPage);
```

- 훅은 컴포넌트 내부에서 로직을 직접 조합할 수 있어서 구조가 더 투명하고 단순
- 반면 HOC는 래퍼가 여러 겹 쌓이면 구조가 복잡해질 수 있음

```js
// HOC 방식
const EnhancedComponent = withAuth(withTheme(withLoading(MyComponent)));

// 훅 방식
function MyComponent() {
  const auth = useAuth();
  const theme = useTheme();
  const loading = useLoading();
}
```

오늘날 새 로직 재사용 방식으로는 훅이 더 자주 선호되지만, HOC도 여전히 라이브러리 설계, 래핑, 호환성 유지 같은 상황에서는 사용됨

Q. 프롭 컬렉션 패턴과 프롭 게터 패턴이 Tanstack Table 라이브러리에서 어떻게 쓰이는지, 둘의 차이까지 포함해서 설명

A. 
프롭 컬렉션: 정해진 props 묶음을 반환
프롭 게터: 사용자 정의 props와 내부 props를 함께 다룰 수 있게 설계

- TanStack Table v8에서는 예전처럼 getHeaderProps 같은 공식 prop getter를 제공X 
- 대신 getToggleSortingHandler, getToggleSelectedHandler 같은 헬퍼를 제공하고, 최종 props 조합은 애플리케이션에서 직접 만듬
- 이때 단순히 props를 묶어 반환하면 프롭 컬렉션 패턴에 가깝고, 사용자 props까지 함께 병합하면 프롭 게터 패턴에 가까움

1. 프롬 컬렉션 예시

```js
function getSortableHeaderProps(header: Header<Person, unknown>) {
  const column = header.column;

  return {
    key: header.id,
    colSpan: header.colSpan,
    onClick: column.getToggleSortingHandler(),
    className: column.getCanSort() ? 'cursor-pointer select-none' : undefined,
    title: column.getCanSort()
      ? `Sort: ${column.getNextSortingOrder() ?? 'clear'}`
      : undefined,
  };
}

// 사용
<th {...getSortableHeaderProps(header)}>
  {flexRender(header.column.columnDef.header, header.getContext())}
</th>
```

- 필요한 props를 한 번에 묶어 준다
- 호출하는 쪽은 그냥 펼쳐서(...) 쓴다
- 사용자 정의 props를 따로 병합하는 구조는 아니다


2. 프롬 게터 예시
```js
function getRowProps(
  row: Row<Person>,
  userProps: React.HTMLAttributes<HTMLTableRowElement> = {},
): React.HTMLAttributes<HTMLTableRowElement> & { key: string } {
  const userOnClick = userProps.onClick;

  return {
    key: row.id,
    ...userProps,
    className: [
      'table-row',
      row.getIsSelected() ? 'selected' : '',
      userProps.className ?? '',
    ]
      .filter(Boolean)
      .join(' '),
    onClick: (e) => {
      userOnClick?.(e);
      row.getToggleSelectedHandler()(e);
    },
  };
}

// 사용
<tr {...getRowProps(row, { className: 'hover:bg-muted' })}>
  {row.getVisibleCells().map((cell) => (
    <td key={cell.id}>
      {flexRender(cell.column.columnDef.cell, cell.getContext())}
    </td>
  ))}
</tr>
```

- 내부에서 필요한 props를 만든다
- 사용자가 넘긴 props도 받는다
- 두 값을 병합한다
- 이벤트 핸들러 충돌도 직접 조정한다
