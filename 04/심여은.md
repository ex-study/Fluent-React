> 파이버는 상태를 저장하고 수명이 긴 반면, 리액트 엘리먼트는 임시적이고 상태가 없다. ... 파이버를 '특정 시점에 존재하는 실제 컴포넌트 트리를 나타내는 리액트의 내부 구조' 라고 설명합니다.

- **React Element**: `<Button />` 같은 JSX가 만들어내는 일반 객체. 매 렌더마다 새로 생성되고 버려짐 (불변, 일회용)
- **Fiber**: 그 엘리먼트에 대응하는 내부 작업 단위. 컴포넌트가 마운트될 때 한 번 만들어지고, 이후 렌더에서는 **재사용하면서 속성만 갱신**됨. state, hooks, effect 목록 등이 여기 붙어 있음.

그래서 "수명이 길다"는 건 컴포넌트가 언마운트될 때까지 같은 파이버 객체가 살아있다는 뜻

---

> 파이버 노드가 생성되면 파이버 재조정자는 ...

> 파이버 노드는 언제 생성되는거지?

**컴포넌트가 최초로 마운트될 때** 생성.
ex) `<App>` 안에 `<Header />`가 처음 나타나면 Header에 대한 파이버 노드 생성
이후 리렌더에서는 새로 만드는 게 아니라 기존 파이버를 복제(clone)해서 업데이트. 컴포넌트가 조건부로 새로 나타나면 그때도 새 파이버가 생기고, 사라지면 파이버도 정리됨.

---

> 작업 루프는 루트 파이버 노드에서 시작해 컴포넌트 트리를 따라 내려가며 업데이트가 필요하면 각 파이버 노드를 '더티'로 표현합니다.

> rhf에서도 변경된 값이 있으면 그걸 dirty로 표현하는데, 같은 개념일까?

**Dirty Flag 패턴** (또는 Dirty Bit 패턴)
핵심 아이디어는 "비싼 연산을 매번 하지 말고, 변경이 생겼을 때 표시만 해두고, 나중에 필요할 때 한꺼번에 처리하자"

- **React Fiber**: state 바뀜 → dirty 표시 → 다음 렌더 사이클에서 처리
- **RHF**: 필드값 변경 → dirty 표시 → 폼 제출/검증 시 활용
- **게임 엔진**: 오브젝트 위치 변경 → dirty → 다음 프레임에서 재계산

> RHF는 Fiber처럼 트리 탐색을 두 번 해서 변경을 감지하나?

**Fiber**: 컴포넌트 트리를 깊이 우선으로 내려갔다가(render), 다시 올라오면서(complete) DOM 변경사항을 모으는 **두 번의 순회**가 필요

**RHF**: 트리가 아니라 **플랫한 key-value 저장소**. 내부적으로 `formValues`라는 객체에 필드값을, `dirtyFields`라는 객체에 dirty 상태를 각각 들고 있어요. 구조를 단순화하면:

```ts
// RHF 내부 (간략화)
const formValues = { name: "여은", email: "" };
const defaultValues = { name: "", email: "" };
const dirtyFields = { name: true, email: false };
// name: "여은" !== "" → dirty
// email: "" === "" → clean
```

필드값이 바뀔 때마다 `defaultValues`와 직접 비교해서 즉시 dirty 여부를 판단함.
구독(subscription) 기반으로 변경된 필드만 알림 보냄
**O(1)로 해당 필드만 체크** (해시맵)

---

> 파이버 재조정은 더블 버퍼링과 비슷하다. 업데이트가 발생하면 현재 파이버 트리가 포크되어 주어진 사용자 인터페이스의 새로운 상태를 반영하도록 업데이트된다. 이를 렌더링이라고 한다.

> 더블 버퍼링이 뭔지

- 게임이나 그래픽에서 쓰는 기법
- 화면에 보여주는 버퍼(A)와 그리는 중인 버퍼(B) 두 개를 두고, B가 완성되면 A와 교체
  => 사용자는 항상 완성된 화면만 보게 되니까 깜빡임 X
- React도 마찬가지로 current 트리(지금 화면에 보이는 것)와 work-in-progress 트리(준비 중인 것) 두 개를 유지함

> 파이버 트리가 포크된다는건 github 포크랑 같나? 즉 메인 트리에 의존성을 갖는 복사된 트리가 생기는건가?

- current 트리를 기반으로 work-in-progress 트리를 만들고(복제),
- 거기서 변경사항을 적용한 뒤, 완성되면 그게 새 current가 됨

---

> 렌더링이 중단 가능한 듯 보이는 이유는 리액트 스케줄러가 5밀리초마다 실행을 메인 스레드로 돌려주기 때문입니다.

- 이전 방식

  - render phase에서 100개 컴포넌트를 처리해야 한다고 치면,
  - 옛날 스택 방식은 100개 다 끝날 때까지 메인 스레드를 독점
  - 그 동안 클릭, 스크롤, 애니메이션 전부 멈춤.

- 파이버 동작 방식

  1.  파이버 n개 처리
  2.  5ms 경과했는지 체크
  3.  경과했으면 → 작업을 **일시정지**하고 메인 스레드를 브라우저에 돌려줌 (이 사이에 클릭, 애니메이션 등 처리 가능)
  4.  브라우저가 할 일 끝나면 → 다시 이어서 파이버 처리

- 실제로 병렬 실행이 아니라, 잘게 쪼개서 번갈아 실행하는 **협력적 스케줄링**
- 커밋 phase는 동기적으로 한 번에 실행됨
- 중단 가능한 건 render phase

---

> [!note]
> renderLanes는 업데이트가 처리되는 레인을 나타내는 비트마스크입니다.

- **레인(Lane)**: 업데이트의 우선순위를 나타내는 값
- 렌더레인: 이번에 처리할 레인들의 조합

```ts
// 개별 레인 (각각 비트 하나)
SyncLane        = 0b0010
DefaultLane     = 0b0100
TransitionLane1 = 0b1000

// renderLanes = 이번에 처리할 레인들의 조합을 비트 ㅒORㅇ
renderLanes = SyncLane | DefaultLane
            = 0b0010 | 0b0100
            = 0b0110  ← "Sync랑 Default 둘 다 처리해"
```

---

> 리액트 컴포넌트를 변경하면 우선순위를 비롯한 여러 특성에 따라 레인이 할당됩니다.

> 어떤 특성이 있을 수 있지?

대표적으로:

- **이벤트 종류**: 클릭/키보드 입력 → 높은 우선순위(SyncLane), 호버/스크롤 → InputContinuousLane
- **startTransition 사용 여부**: transition으로 감싸면 TransitionLane 할당 (낮은 우선순위)
- **Suspense**: 데이터 로딩 관련 업데이트에 별도 레인
- **useDeferredValue**: 지연된 값 업데이트에 낮은 우선순위 레인
- **오프스크린(Offscreen)**: 화면에 안 보이는 컴포넌트는 IdleLane (가장 낮음)

---

> 업데이트 우선순위를 지정하는 것 외에 다른 역할도 있습니다. renderLanes는 리액트가 동시성을 더 잘 관리하도록 지원합니다. 리액트는 타임 슬라이싱(time slicing)이라는 기술을 사용해 실행 시간이 긴 업데이트를 더 작고 관리하기 쉬운 덩어리로 분할합니다. 이 과정에서 renderLanes가 주된 역할을 하는데, 리액트가 어떤 업데이트를 먼저 처리할지, 어떤 업데이트를 미룰지 결정하기 때문입니다.

> 무슨 소리인지 모르겠음
> 타임 슬라이싱에서 renderLanes가 왜 주된 역할을 하는지?
> 이게 동시성이랑 무슨 연관?

- **타임 슬라이싱**: 5ms씩 쪼개서 실행하는 기법
- **renderLanes가 왜 중요한지**: 타임 슬라이싱으로 작업을 쪼개면, 중간에 더 급한 업데이트가 들어올 수 있어요. 이때 renderLanes를 보고 "지금 처리 중인 건 TransitionLane인데, SyncLane 업데이트가 들어왔네 → 지금 하던 거 중단하고 SyncLane 먼저 처리"라는 판단을 합니다.
- **동시성과의 관계**
  - React의 "동시성(Concurrent)"은 실제 병렬 실행X, "여러 업데이트를 우선순위에 따라 끼워넣고 전환할 수 있다"
  - 필요한 요건
    1. 작업을 중간에 멈출 수 있어야 함 → **타임 슬라이싱**
    2. 뭘 먼저 할지 판단할 수 있어야 함 → **renderLanes**
    3. 파이버 구조 - 작업을 객체 단위로 쪼갤 수 있음

---

> 패시브 효과는 렌더링 단계에서 수행되지 않으므로, 사용자 인터페이스를 개발자가 원하는 상태로 만드는 데 필요한 최소 업데이트 집합의 계산 시간에 영향을 주지 않습니다.

- **패시브 효과 = `useEffect`**

렌더링 과정을 타임라인으로 보면:

1. **Render phase** — 컴포넌트 함수 호출, 변경사항 계산
2. **Commit phase** — DOM 반영 (여기서 `useLayoutEffect` 실행)
3. **브라우저 페인트** — 화면에 그림
4. **패시브 효과 실행** — `useEffect` 콜백이 비동기로 실행됨

- `useEffect`는 화면이 이미 그려진 **뒤에** 비동기로 실행
- "UI를 원하는 상태로 만드는 데 필요한 계산(1~2단계)"에 시간을 더하지 않음
- **`useEffect`는 화면 업데이트를 블로킹하지 않는다**

### 복습하기

#### 1. 리액트의 재조정(Reconciliation)이란?

state나 props가 바뀌었을 때, **이전 트리와 새 트리를 비교해서 실제 DOM에 최소한의 변경만 적용하는 과정**이에요. 전체 DOM을 처음부터 다시 그리는 건 비싸니까, "뭐가 달라졌는지"만 찾아내서 그 부분만 업데이트하는 거죠.

#### 2. 파이버 데이터 구조의 역할

파이버는 **각 컴포넌트의 현재 상태(state, props, hooks, effect 등)를 메모리에 보관하는 내부 작업 단위**예요. 컴포넌트당 하나의 파이버 노드가 대응되고, 이 노드들이 트리를 이루면서 "지금 이 순간 앱이 어떤 상태인지"를 표현합니다. 또한 파이버 단위로 작업을 쪼갤 수 있어서 렌더링을 중단/재개할 수 있게 해주는 게 핵심 역할이에요.

#### 3. 왜 트리가 두 개 필요한가 (더블 버퍼링)

**current 트리**(지금 화면에 보이는 상태)와 **work-in-progress 트리**(다음 상태를 준비 중인 것) 두 개를 유지합니다. 이유는:

- WIP 트리에서 작업하는 동안 사용자는 current 트리 기반의 안정적인 화면을 계속 볼 수 있음
- WIP 작업이 중단되거나 버려져도 current 트리에는 영향 없음 (안전하게 롤백 가능)
- WIP가 완성되면 포인터만 교체해서 WIP가 새 current가 됨

하나만 있으면 업데이트 도중에 화면이 깨지거나 중간 상태가 노출될 수 있어요.

#### 4. 애플리케이션이 업데이트되면 어떻게 되나요

순서대로 보면:

1. state 변경이 발생하면 해당 파이버에 **업데이트가 예약**되고, 우선순위에 따라 **레인이 할당**됨
2. **Render phase** — current 트리를 기반으로 WIP 트리를 만들면서, 변경된 컴포넌트 함수를 호출하고 이전과 비교해서 뭐가 달라졌는지 계산함. 이 과정은 5ms 단위로 쪼개져서 실행되고, 더 급한 업데이트가 오면 중단될 수 있음
3. **Commit phase** — 계산된 변경사항을 실제 DOM에 동기적으로 반영하고, `useLayoutEffect` 실행
4. **브라우저 페인트** — 화면에 그림
5. **패시브 효과** — `useEffect`가 비동기로 실행됨
