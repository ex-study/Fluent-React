> 리액트 스케줄러가 5ms마다 실행을 메인 스레드로 돌려주기 때문입니다.
- React Scheduler의 역할은 무엇인가?
	React Scheduler는 렌더링 작업을 언제 실행할지 조정하는 시스템이다.
	React는 모든 렌더링 작업을 한 번에 처리하지 않고 작업을 작은 단위로 나누어 실행하고, 일정 시간이 지나면 브라우저에게 다시 제어권을 넘겨준다.
	즉 Scheduler의 역할은 다음과 같다.
	- 렌더링 작업을 **스케줄링**    
	- 작업을 **시간 단위로 나누어 실행**    
	- **우선순위(priority)** 관리    
	- 브라우저 이벤트가 **막히지 않도록 제어권 반환**
	
- 실제 어떤 동작을 하는지 예시가 궁금하다.
	JS는 싱글 스레드로 동작하는데, 따라서 React가 렌더링을 오래 수행하면 메인 스레드 블로킹이 발생한다.
	이를 해결하기 위해 React Scheduler는 Time Slicing이라는 방식을 통해 해결했는데, 이것이 바로 렌더링 작업 단위를 5ms로 나누어 실행하는 것이다.
	이렇게 하면 브라우저는 작업 중간중간 사용자 입력처리, 스크롤 처리 ,애니메이션 처리 등을 수행할 수 있다.

예를 들어 아래처럼 엄청나게 많은 양의 리스트를 렌더링 한다고 가정해보자
```
function List() {
  return new Array(10000).fill(0).map((_, i) => <Item key={i} />);
}
```
기존 Stack Reconciler 방식으로는 총 1만개의 Item이 렌더링이 완료될 때까지 브라우저는 멈추가 된다.

그러나 Fiber + Scheduler 방식의 경우, 작업 단위를 Fiber로 나누고 5ms가 지나면 브라우저에게 제어권을 반환하게 된다.

```
render Item1
render Item2  // 5ms 경과

yield (브라우저에게 제어권 반환) 
- input event
- scroll
- animation 등을 브라우저가 처리

완료되면 다시 React가 실행됨
render Item3
render Item4
render Item5
```

## **정리**
### **Stack Reconciler vs Fiber**
React Fiber는 기존에 사용되던 **Stack Reconciler의 단점을 보완하기 위해 등장한 아키텍처**이다.

#### **Stack Reconciler의 단점**
- Stack은 **LIFO 방식**으로 동작한다.
- 현재 진행 중인 작업을 **중단할 수 없다.**
따라서 렌더링 작업이 커지면 다음 문제가 발생한다.
- 작업이 **16ms 이상** 걸릴 수 있음
- 브라우저는 **60fps 렌더링을 유지하지 못함**
- 사용자에게 **프레임 드롭(jank)** 발생
#### **Fiber의 개선점**
Fiber는 **렌더링 작업을 작은 단위로 분할하고 중단할 수 있다.**
- 거대한 렌더링 작업을 **작은 작업 단위로 분할**
- 각 작업 단위가 **Fiber 객체 하나**
즉,
> 하나의 긴 작업 대신 여러 개의 작은 작업으로 처리한다.

작은 작업 사이에는 **브라우저에게 제어권을 돌려주는 시간**이 생긴다.

이 시간 동안
- 더 **우선순위가 높은 작업**이 들어오면
- 진행 중이던 렌더링을 **잠시 중단**
- 우선순위가 높은 작업을 **먼저 처리**

## **React의 동시성**
React에서 이야기하는 **동시성(Concurrency)** 은

> UI 업데이트 작업을 **나눠서**, **중단하고**, **우선순위를 바꿔가며 처리하는 능력**

을 의미한다.
즉 React는 다음과 같이 동작할 수 있다.

```
1. 렌더링 시작
2. 중간에 사용자 입력 발생
3. 렌더링 잠깐 멈춤
4. 사용자 입력 먼저 처리
5. 다시 렌더링 이어서 진행
```

### **React가 가능한 3가지 동작**
#### **1. Interrupt (중단)**
작업 중간에 렌더링을 멈출 수 있다.

```
render A
render B
render C

(사용자 클릭)

렌더링 중단
클릭 이벤트 처리
```

#### **2. Priority (우선순위)**
React는 작업마다 **우선순위(priority)** 를 가진다.

| **작업**       | **우선순위** |
| ------------ | -------- |
| input typing | 매우 높음    |
| 버튼 클릭        | 높음       |
| 리스트 렌더링      | 낮음       |
| 백그라운드 데이터    | 매우 낮음    |

예를 들어,
- 매우 큰 List를 렌더링하는 중
- Input 이벤트 발생
React는 다음과 같이 처리한다.
1. 리스트 렌더링 **일시 중단**
2. Input 이벤트 **먼저 처리**
3. 다시 리스트 렌더링 **재개**

#### **3. Restart (재시작)**
더 중요한 작업이 들어오면 기존 렌더링을 **버리고 다시 시작할 수 있다.**

```
리스트 1000개 렌더링 시작
↓
사용자 검색 입력
↓
기존 렌더링 폐기
↓
새 검색 결과 렌더링
```


> React의 동시성은 **병렬 실행이 아니다.**

JavaScript는 여전히 **Single Thread**이다.
React가 하는 일은 다음과 같다.
- 작업을 **작게 쪼갠다**
- 작업 사이에 **브라우저에게 제어권을 반환한다**
- 틈틈이 작업을 계속 수행한다.
즉,
```
작업 A
브라우저

작업 B
브라우저

작업 C
브라우저
```
이 방식으로 동작한다.

## FiberNode / React Element
### React Element
컴포넌트 호출 시 반환되는 객체로, 우리가 그려려는 UI를 설명하는 불변 객체이다.
JSX는 React Element를 만드는 문법으로, createElement 메서드를 사용하면 단순한 JS 객체로 변환된다.

### FiberNode
FiberNode는 React 내부에서 사용되는 작업단위 객체이다.
리액트 엘리먼트가 UI에 대한 설명이라면, Fiber은 UI 업데이트를 수행하고, 실행하는 구조이다.

## 더블 버퍼링
리액트는 재조정을 더욱 효율적이고, 안정적으로 만들기 위해 더블 버퍼링 구조를 사용한다.
즉, Fiber Tree를 두 벌로 관리하는 것인데
Current Tree / Work-in-Progress Tree 로 관리한다.

### Current Tree
현재 화면에 보이는, 실제 DOM과 완벽하게 동기화된 Tree로 원본 사진이라고 생각하면 쉽다.
사용자가 현재 보고있는 UI를 나타내며, 그 다음 업데이트를 위한 기준점이 된다.

### Work-in-Progress Tree
상태 변경이 발생했을때, Current Tree를 그대로 복제해서 만든 사본 청사진이다.
모든 변경사항은 이 트리에서 일어나고, 실제 DOM에는 아무런 영향이 없다.

### Alternate (Fiber 연결)
Current Tree와 Work-in-Progress Tree의 Fiber은 서로 연결되어있다.
```
current fiber
   ↕ alternate
workInProgress fiber
```
이 연결을 통해 React는 이전 상태와 새 상태를 동시에 비교할 수 있다.

## 렌더링 전체 흐름
### Render Phase (Reconcilliation)
새 UI를 계산하는 단계이다.
여기서 React는 
- 새 Fiber Tree 생성
- diff 계산
- Effect 목록 생성
등을 한다
ex)
```
<div>
  <h1>Hello</h1>
</div>

↓ p태그 추가

<div>
  <h1>Hello</h1>
  <p>World</p>
</div>
```

위 경우, React는 p 추가 라는 작업을 기록하게 된다.
이 단계에서는 
- DOM을 수정하지 않고
- Interrupt이 가능하고
- Effect List (add p node ... delete div node..)를 생성한다.

### Commit Phase
RenderPhase가 끝나면 React는 Commit Phase로 넘어가게 되는데, 여기서는 실제 DOM이 변경된다.
여기서는
- Interrupt가 불가능하고 (UI업데이트 중 Interrupt가 발생하면 UI가 꺠질 수 있기 떄문)
- 속도가 매우 빠르다

## 전체 흐름
> 사용자가 버튼을 클릭했다. (setState 실행)

1. Update 발생
	React는 Update Queue에 상태를 추가한다.
2. Render Phase 시작
	Fiber를 순회하며 diff 계산, effect 생성한다.
```
Current Tree
↓
Work-in-Progress Tree 생성
```

3. Work-in-Progress Tree 완성
4. Comit Phase
	React는 effect를 실행한다
	- DOM insert
	- DOM update
	- DOM delete
5. Tree Swap
	리액트는 두 트리를 교체한다. (current <-> workInProgress)
	이제 workInProgress가 current tree가 된다.
